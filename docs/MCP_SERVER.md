# MCP Server

> Phase 1 (#11/#12 tail) — a standalone **Model Context Protocol** server under
> `backend/app/mcp/` that re-exposes NovaSight's grounded chat tools to *external*
> MCP clients (e.g. Claude Desktop, IDE assistants).

The in-process AI chat (`/api/v1/ai/chat`) lets NovaSight's own model answer questions
by calling a fixed set of grounded tools. This server makes those **same tools**
available to any MCP-capable assistant, so a user can point their own client at their
tenant's governed semantic layer.

---

## What it is (and is not)

It is a **thin protocol adapter**. It does not query ClickHouse, call Cube, or talk to
an LLM. Every tool call is forwarded to the existing, already-audited backend HTTP API,
carrying the caller's `Authorization` header verbatim. The backend stays the single
boundary for the things that matter:

| Concern | Where it lives | Why the MCP server stays thin |
| --- | --- | --- |
| **Auth + tenancy** (golden rule 2) | Backend `get_tenant_context` (from the verified JWT) | The MCP process never parses, defaults, or trusts a tenant id. A missing/invalid token fails closed at the backend (401/403). |
| **Grounding + validation** (golden rule 3) | Backend `/semantic/*` + `/ai/query` | The tools call only governed, validated endpoints — no raw-table or arbitrary-SQL path is added. |
| **Config** (golden rule 1) | `settings.mcp` | Backend URL, bind address, transport, and limits all come from the environment. |

```
external MCP client ──(MCP over streamable-http, Authorization: Bearer <JWT>)──▶ app.mcp.server
                                                                                      │  forwards the same header
                                                                                      ▼
                                                          NovaSight API  /api/v1/semantic/models
                                                                         /api/v1/semantic/query
                                                                         /api/v1/ai/query
```

## The tools

The tool **names and descriptions** are imported from the in-process chat service
(`app/ai/chat/service.py`) so the external surface never drifts from the internal one.
Their input schemas are generated by FastMCP from the handler signatures.

| Tool | Maps to | Input | Returns |
| --- | --- | --- | --- |
| `list_semantic_models` | `GET /semantic/models` | — | Governed models with their measures + dimensions. **Call this first** to discover valid names. |
| `query_semantic_model` | `POST /semantic/query` | `measures[]`, `dimensions[]`, `limit?` | `{ columns, rows, row_count, truncated }` |
| `nl_to_sql` | `POST /ai/query` | `question` | `{ sql, columns, rows, row_count, truncated }` |

Row results are capped at `settings.mcp.max_tool_rows` (default 50, mirroring the
in-process chat loop) so a large result can't blow the client's context window;
`truncated` is `true` when rows were dropped, while `row_count` keeps the backend's
full count.

> The in-process chat (`/api/v1/ai/chat`) also exposes a fourth tool, `nl_to_chart`,
> which generates a saveable chart the user can pin to a dashboard (#12). The external
> MCP server **intentionally does not** re-expose it: chart/dashboard persistence is an
> in-app concern, and an external client has no NovaSight UI to pin into. The MCP
> surface stays the three read-only, query-shaped tools above.

### Errors (fail closed, never leak internals)

Backend failures are surfaced as MCP `ToolError`s with safe messages:

- **No / invalid token** → "Not authenticated or not authorized for this tenant…"
- **Ungrounded reference or bad request** (422) → the backend's safe `detail`
  (e.g. `Unknown measure(s): bogus`).
- **Semantic layer / LLM provider down** (503) → "temporarily unavailable…"
- **Unexpected status or transport failure** → a generic message; the detail is logged,
  never returned.

## Authentication

The server is a **transparent bearer-token forwarder**. The client sends the same
tenant JWT it would send to the NovaSight API:

```
Authorization: Bearer <token>
```

over the MCP HTTP transport, and the server relays it to the backend on every tool
call. Tool *discovery* (`list_tools`) is unauthenticated — the tool names/schemas carry
no tenant data — but every tool *execution* is authenticated by the backend. See
[AUTH.md](AUTH.md) for how tokens are issued/verified (OIDC, password mode, or the dev
stub).

> Only HTTP transports (`streamable-http`, `sse`) carry headers. Under `stdio` there is
> no request, so the tools fail closed with a clear "missing bearer token" error.

## Running it

### Compose (the `mcp` role)

The stack runs it as its own service — the same backend image, a different command:

```bash
docker compose -f infra/compose/docker-compose.yml up -d mcp
```

It waits for the `api` service to be healthy and is reachable at
`http://localhost:${MCP__PORT}/mcp` (default `8900`). Compose sets
`MCP__BACKEND_BASE_URL=http://api:8000/api/v1` automatically (the in-cluster API URL).

### Standalone

```bash
MCP__BACKEND_BASE_URL=http://localhost:8000/api/v1 python -m app.mcp.server
```

The server fails closed at startup (exit 1) if `MCP__BACKEND_BASE_URL` is empty.

### Pointing a client at it

Most clients accept a streamable-http URL plus a static header. For example, a generic
MCP client config:

```json
{
  "mcpServers": {
    "novasight": {
      "url": "http://localhost:8900/mcp",
      "headers": { "Authorization": "Bearer <your-tenant-token>" }
    }
  }
}
```

## Configuration (`settings.mcp`, env group `MCP__`)

All values have safe, environment-identical defaults except `backend_base_url`, which
points at infrastructure and so has an empty sentinel default (the server refuses to
start until it is set) — see [CONFIGURATION.md](CONFIGURATION.md).

| Setting (`MCP__…`) | Default | Purpose |
| --- | --- | --- |
| `BACKEND_BASE_URL` | _(empty → refuses to start)_ | API base URL **including** the version prefix, e.g. `http://api:8000/api/v1`. |
| `HOST` / `PORT` | `0.0.0.0` / `8900` | Bind address + port for the MCP transport. |
| `TRANSPORT` | `streamable-http` | `streamable-http` \| `sse` \| `stdio`. |
| `PATH` | `/mcp` | Route for the streamable-http transport. |
| `STATELESS` | `true` | Each request is self-contained (no server-side session); suits a token-forwarding proxy and horizontal scaling. |
| `REQUEST_TIMEOUT_SECONDS` | `30` | Timeout for upstream calls to the API. |
| `MAX_TOOL_ROWS` | `50` | Row cap applied to tool results. |
| `ALLOWED_HOSTS` / `ALLOWED_ORIGINS` | `[]` | When non-empty, enables DNS-rebinding protection limited to these `Host` / `Origin` values (wildcard port supported, e.g. `mcp.example.com:*`). |

## Layout

```
backend/app/mcp/
  __init__.py          — package docstring + public re-exports
  backend_client.py    — AnalyticsBackendClient (async proxy) + BackendError
  server.py            — build_server() (FastMCP + the 3 tools) + main() entrypoint
backend/tests/test_mcp_server.py — proxy status mapping, header forwarding, row cap,
                                    fail-closed build, and tool-closure behaviour
```

The FastMCP transport plumbing (injecting the Starlette request — and thus the
`Authorization` header — into each tool's context) is SDK behaviour; the tests drive
the tool functions directly with a stand-in context and a mock HTTP transport.
